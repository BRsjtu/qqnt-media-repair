# 批量修复工作流

本流程覆盖两种独立任务：兼容性说明中定义的旧版文件卡片引用修正，以及有条件的媒体原件路径补回。两种任务不可混为一类，也不能以一种任务的结果推断另一种。CLI 命令名和参数以工具当前版本的帮助信息为准；本文说明操作关口和结果，不预先承诺尚未稳定的命令接口。

旧版 `FILE` subtype 1 profile 仍是数据库修复默认值。Subtype 7 使用独立的 `legacy-file-subtype7-v1`，必须在 `scan` 时显式传 `--profile legacy-file-subtype7-v1` 并创建新计划；不要复用 subtype 1 的 plan。Subtype 7 数据库 pilot 和完整性检查已通过，一条原聊天 PDF 卡片成功打开本地 PDF，但页面内容没有目视验证。该证据只支持已验证的记录布局和代表案例，不代表所有扩展名或页面；仍须按 profile、用户授权和常规 dry-run/sample gate 执行批量操作。

## 1. 定位并确认数据

1. 根据配置和应用状态识别当前 QQ 安装及当前账号。解析快捷方式、junction 和路径别名，并在本机运行记录中记下映射关系。不能只根据目录名或“看起来最新”来选择数据根目录。
2. 若账号或目标位置不明确，先向用户核实。公开输出不得包含账号标识或私有路径。
3. 通过已有且获授权的本地流程取得匹配的数据库密钥，并确认它能打开所选数据库。密钥材料留在本机，不新增密钥提取工具，不记录或传输密钥。

## 2. 稳定读取并清点

1. 关闭 QQ，并确认进程已退出后再建立稳定读取状态。按 SQLite 要求将源数据库及 WAL/SHM sidecar 一并处理。不得修改、截断或丢弃 WAL 文件。
2. 在临时工作目录中对一致状态的本地数据快照进行操作。临时数据库快照同时最多保留一份；运行结束后按用户要求安全清理临时快照，仅按保留策略留下加密回滚包。
3. 清点所有单聊和群聊中符合当前配置文件的记录。分别记录合格记录、未处理媒体和带明确原因的跳过记录。路径补回只考虑记录明确指出的 `Ori` 原件路径；未被当前索引命中的项目不能据此认定原文件已丢失。
4. 对每个候选原文件读取实际字节并计算内容哈希。仅有文件名或预期哈希字段，不能证明原文件存在或匹配。

## 路径补回的额外关口

1. 用只读清点建立候选。只接受原记录中明确写出的缺失 `Ori` 路径；不从缩略图、文件名、时间或同尺寸文件推测目标。
2. 对每个来源核验文件身份、大小、MD5 和 SHA-256。来源身份有冲突、记录有冲突、路径越界或来源字节不能复核时，排除该目标并说明原因。
3. 检查 dry-run 清单中的媒体类别、原记录位置、目标路径、来源身份与待增加空间。`not_in_fast_index` 是当前索引未命中状态，不代表媒体丢失。
4. 代表案例按媒体类别验证 QQ 原聊天中的实际行为。图片已有原聊天和原生查看器验证。视频原件路径补回与封面缓存修复是两步：如果 `45404` 声明的封面路径也缺失，再用 `video_cover_repair.py` 从已核验 MP4 解码首帧并创建派生 PNG。此流程在 QQ 9.9.31-49738 的代表案例中通过原聊天封面、播放按钮及原生播放器验证；该结果不外推到未知布局或版本。视频和文件原件路径补回仍是显式 opt-in；文件类别须在使用者自己的 QQ 环境验证实际打开行为。
5. 仅在用户授权后应用已审阅计划。只创建不存在的目标，不覆盖现存文件、不修改消息数据库、不清除未知失败标记。若中途失败，保留明确的部分完成清单并单独报告，不能把计划数说成已创建数。

视频封面是从本机原片生成的派生缓存，不是云端原封面或丢失原片的恢复。扫描器须读取消息字段 `45404` 的明确路径；不得只凭常见文件夹布局自行构造目标。`video_cover_repair.py` 默认 dry-run，应用前核验 QQ 版本、原片字节、缺失目标及现存缓存状态；只写入不存在的封面路径。

## 3. 生成计划并验证配置文件

1. 修改前生成 dry-run 计划。计划需标明配置文件、聊天范围、目标记录、原文件精确映射、内容哈希、备份/回滚位置，以及合格、跳过、未处理记录数量。
2. 在 QQ 中核对 1–2 条原始文件卡片与计划映射。这只是配置文件抽查。检查通过后，应继续处理用户任务授权覆盖的整批合格记录；不能以抽查为由停下来逐条询问许可。
3. 不符合当前 schema/标记配置文件，或无法确认原始字节的记录，必须排除在修改之外并报告原因。不得猜测性清除失败标记。新 schema 必须先建立并验证单独命名的配置文件。

## 4. 应用修改并保留回滚能力

1. 修改前确认已取得针对本次任务的授权。若用户已授权修复，该授权覆盖计划中的整批合格记录。
2. 创建加密回滚包，只包含受影响的原始记录及恢复所需元数据。密钥材料单独保护，不得放入报告或版本库。
3. 在稳定工作副本上应用计划修改，保留无关字段和记录。QQ 打开时不得修改实时数据库。
4. 发布前检查源锁定/WAL 状态和事务提交边界，运行工具支持的数据库完整性检查，并确认没有非预期记录变化。检查失败时不得发布；应从工作快照或回滚包恢复并报告失败。
5. 使用工具支持的安全替换流程发布。QQ 或其他写入进程持有数据库时，不得替换数据库。

## 5. 验证并收尾

1. 重新打开 QQ，确认原卡片预览和双击操作可用。
2. 抽查有代表性的已修复消息，覆盖单聊、群聊以及批次较早和较新的部分。明确记录任何 UI 验证限制。
3. 分别报告按原件/预览分开的创建路径数、按原因跳过、失败和未处理数量；单列已在 QQ UI 验证的类别及样本数。路径数不是独立照片、媒体或聊天数。可包含运行标识和回滚是否可用，但不得包含私有标识、原始消息内容、密钥或敏感本地路径。
4. 当前支持范围之外的媒体应记为未处理/索引来源中未找到原文件。原件仍可能存在于手机或备份中，即使不在当前本地索引内。不得据此推断服务器过期或永久丢失。
5. 用户要求回滚或验证失败时，使用加密受影响行回滚包和工具支持的回滚流程。回滚后检查数据库完整性及代表性原始行为，并报告结果。

## 公开内容边界

不得提交、公开或粘贴数据库文件、WAL/SHM 文件、密钥/密钥文件、账号标识、消息内容、原文件名、私有哈希、快照、回滚包或运行报告。示例仅使用通用路径，例如 `D:\QQ\<account>` 和 `D:\QQRepairRuns\run`。
