# 兼容性与支持的记录配置文件

## 已验证基线

目前的兼容性结论仅限于观察和验证过的以下环境：

- Windows QQ 9.9.31-49738，x64。
- Python 包 `sqlcipher3==0.6.4`，使用 CPython 3.13 Windows x64 `.pyd` 适配器，并在使用前校验预期哈希（底层为 SQLCipher 4）。

该基线不代表所有 QQ 版本、数据库布局或适配器构建都可用。请在本机运行记录中保留工具报告的版本和适配器身份。不得将初始基线宣传成广泛兼容。

## 命名的旧版文件卡片配置文件

只有同时确认以下条件，记录才符合当前范围：

- 属于旧版 `FILE` 元素，且 `type=3`、`subtype=1`。
- 旧版 ASCII 32 位 MD5 字段 `45407` 标识该文件卡片媒体。
- 字段 `45507` 存在过时失败标记 `-7003`，或字段 `45509` 存在无效标记。
- 原始文件字节在本地存在且可读取；必须从这些实际字节计算哈希。

不得假定所有失败媒体记录都使用此配置文件。不得仅因为记录较旧或媒体不可用就清除标记。不得声称所有过期媒体均可恢复。

## 显式 opt-in 的旧版 FILE subtype 7 配置

新增独立配置 `legacy-file-subtype7-v1`，默认 profile 仍为上面的 subtype 1。扫描 subtype 7 时必须显式指定 `--profile legacy-file-subtype7-v1` 并建立独立计划。该配置仅接受 `type=3`、`subtype=7`、单一合法 ASCII 32 位 `45407`、有效大小、匹配的文件名/扩展名与本地路径、无冲突的记录；`45406` 不得非法或与 `45407` 矛盾，只有该字段缺失/非规范，或记录同时含可确认的旧失败标记时才 eligible。若存在失败字段，只接受完整精确标记组合 `45507=-7003`、`45509=1`、`45554=“传输失败，请稍后重试”`；未知值、缺项、混合标记和字段冲突都会排除。来源文件必须在获准本地来源中通过实际字节大小、MD5 和 SHA-256 校验。

匹配后只规范化该消息的 40800 内容：写入本地原件路径、规范 16 字节 `45406`、适配的扩展名字段，并仅移除精确识别的旧标记；保留其他字段、type/subtype 及受支持的 `::NTOSFull::` 本地路径。工具计划包含加密 before/after 行记录，支持条件回滚。数据库 pilot 和完整性检查通过；一条原聊天 PDF 卡片已成功打开本地 PDF，文档结构解析与本地渲染通过。此证据仅覆盖该 profile 的 PDF 代表案例，不构成对所有扩展名的兼容承诺。

## 明确图片路径补回配置文件

新增命名配置：`explicit-media-original-path-rehydration-v1`。通用候选条件是：聊天记录给出了明确原件 `Ori` 路径；该路径在所选本地账号树中缺失；记录身份与来源对应无歧义；另一处本机来源仍有可读原始字节，且大小、实际 MD5 与 SHA-256 均匹配。候选未命中快速索引只表示当前索引没有命中，不能推断原件丢失。默认类别为图片；视频和文件只有显式 opt-in 才进入计划，不因此获得通用 QQ UI 兼容承诺。

普通图片的代表案例已按记录声明的原件及预览路径逐字节补回，并验证原聊天显示和原生图片查看器均可正常打开。

视频原件路径与封面缓存是两个不同目标。视频原件可按消息明确的原件路径补回，但单独补回原片可能仍让聊天卡片显示过期。封面目标必须直接来自原记录字段 `45404`；不得按目录习惯猜路径。`video_cover_repair.py` 会验证对应本地 MP4 来源的大小、MD5 和 SHA-256，解码首帧并创建派生 PNG，不改视频字节或消息数据库，不覆盖已有封面。QQ 9.9.31-49738 的代表案例已验证：补回消息明确指向的缺失封面缓存后，原聊天卡片显示封面和播放按钮，且能启动 QQ 原生播放器。该结论限于此已验证布局和版本，生成的是派生预览，并非恢复云端原封面。

`video_cover_repair.py` 默认 dry-run；生成首帧图需 PyAV（Python 包 `av`）和 Pillow。文件原件路径补回仍须 `--media-kinds file` 显式 opt-in；来源字节和目标路径可核验，不等于 QQ 已验证可打开。Subtype 7 profile 已实现，数据库 pilot 与完整性检查通过；一条原聊天 PDF 卡片成功打开本地文件，PDF 解析及本地渲染也通过。该案例不外推其他格式。Subtype 1 继续是默认 profile；不得套用另一 profile 的规则或把 pilot 说成已普遍验证。

`broad_media_scan.py` 只执行清点和来源验证，不执行补回。`restore_targets` 保存非引用、无元数据冲突的明确缺失路径；可处理的原件目标来自消息原记录中的字段 `45403`，且需位于账号 `nt_qq/nt_data/{Pic,Emoji,Video,File}/.../Ori/...`。目标来自原记录，不能根据缩略图路径猜测原图路径。同一目标出现不同已验证来源时，将其移出目标表并写入阻止及冲突表。工具计划列出的类别仍须遵守上述类别级 UI 验证状态；清点或路径补回本身不等于 QQ 界面验证。

该配置只支持有本机原始字节且路径和身份可确定的情况。正常原件仍在、仅缩略图缺失，不构成已证实损坏。索引提示、路径缺失、错误标记或“已找到候选”均不能代替实际字节验证及相应 QQ 原聊天 UI 验证。原件路径补回只创建不存在的目标，不覆盖既有文件，不改消息数据库，也不清除未知标记；视频封面流程只增加从原片派生的缓存图。原件本已存在、哈希匹配或本地解码成功，均不能证明 QQ UI 无故障；不得仅据此清除未知错误标记。不得用图片案例外推视频、文件、语音或引用媒体的 UI 兼容性。

## 其他 schema 和媒体

未知 QQ 版本、变化后的 schema、不同标记、超出上述已验证配置的媒体或缺少原始字节的记录，均不在当前修复范围内，需先调查。广域清点可以报告这些记录，但不会将其自动列为已修复或可修复。任何扩展都应使用有代表性的单聊和群聊记录验证，确认原始字节和 UI 行为，并建立单独命名的配置文件。范围外记录保持不变，并注明原因。

索引中找不到原件，并不能证明其他位置也没有副本，例如手机或备份。应将其标记为未处理，或“在此索引数据源中未找到原件”；不得推断服务器过期或永久丢失。
